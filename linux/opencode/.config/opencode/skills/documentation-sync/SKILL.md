# Documentation Sync

## What it does

- Updates repository documentation so it matches the current code, behavior, configuration, and developer workflows.
- Finds which docs are affected by a change instead of editing documentation broadly or guessing at product behavior.
- Produces doc updates that explain what changed, what users or contributors need to do differently, and any important limits that remain.

## When to use it

Use this skill when the task involves:
- updating docs after a feature, bug fix, refactor, migration, or config change
- checking whether `README`, guides, setup docs, examples, or API docs still match the codebase
- keeping developer onboarding, local setup, CLI usage, env vars, or integration instructions in sync
- revising documentation as part of a pull request so code and docs land together
- identifying missing doc updates for behavior that changed in a user-visible or contributor-visible way

## Do not use it when

- the task is purely editorial writing with no code or behavior change to anchor it
- the task is broad product messaging, marketing copy, or long-form content strategy
- the documentation is fully generated by tooling and the work is to fix the generator instead
- the request is only to summarize code changes without updating documentation files

## Workflow

1. Inspect the relevant code changes, affected files, and existing docs before writing anything. Determine what behavior, interface, setup step, or workflow actually changed.
2. Identify the smallest set of documentation files that should change. Prioritize high-traffic sources such as `README`, setup guides, command references, API docs, examples, and migration notes.
3. Update docs to reflect the current code truth:
   - describe the new or changed behavior accurately
   - update commands, paths, env vars, flags, config keys, and defaults
   - adjust examples so they still work with the current implementation
   - note required migrations, caveats, or rollout steps when they matter
4. Keep the documentation aligned with the repo's existing voice and structure. Prefer targeted edits over large rewrites unless the current organization is what makes the docs misleading.
5. Verify each doc claim against the code or against commands you actually ran. If something could not be verified directly, say so rather than inventing certainty.
6. In the final handoff, mention which docs were updated, what user-visible or contributor-visible change they now cover, and any documentation gaps that still need product input.

## Guardrails

- Do not invent features, defaults, support guarantees, or roadmap promises that are not present in the code or user request.
- Do not update unrelated docs just to make the change feel comprehensive.
- Do not leave examples, command snippets, or config fragments half-updated; keep names and values consistent everywhere touched.
- Prefer documenting observable behavior and required actions over implementation details unless the audience is contributors.
- When the correct doc location is unclear, choose the most discoverable existing file and note any uncertainty.
- If code and docs appear to disagree in multiple places, anchor edits to the current code and call out any broader cleanup opportunity.

## Verification

- Confirm every updated statement matches the current code, config surface, or verified command behavior.
- Confirm examples, command invocations, env vars, and file paths are internally consistent across touched docs.
- Confirm the changed docs cover the practical impact of the code change, not just its existence.
- Confirm the final report names any assumptions or items that still need human confirmation.
